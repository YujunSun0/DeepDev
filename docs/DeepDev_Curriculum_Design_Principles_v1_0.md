# DeepDev 커리큘럼 설계 원칙 (v1.0)

------------------------------------------------------------------------

# 1. 목적

본 문서는 DeepDev의 **개념(Concept) 선정 기준**, **도메인별 학습 방식**, **확장 로드맵**을 정의한다.

------------------------------------------------------------------------

# 2. 타깃 & 학습 목표

## 2.1 타깃 사용자

- **취준생** (코딩테스트, 기술면접 대비)
- **주니어 개발자** (1~3년차, 실무 기초 확립)

## 2.2 학습 목표 (3가지 모두 해당)

| 목표 | 설명 |
|------|------|
| **실력 척도** | "나는 이 분야 어느 정도 수준인가?" 정량화 |
| **실무 적용** | 실제 개발에 필요한 지식 습득 |
| **면접 대비** | 코딩테스트, 기술면접 대응력 향상 |

------------------------------------------------------------------------

# 3. 주니어 학습 설계 원칙

취준생·주니어가 **오래 기억하고**, **실제로 쓸 수 있게** 학습하도록 설계한다.

## 3.1 핵심 원칙

| 원칙 | 설명 | DeepDev 반영 |
|------|------|--------------|
| **실전 연결** | "왜 배우는가"가 먼저. 추상적 정의보다 **면접/실무 시나리오**로 시작 | 설명·문제에 "면접에서 이렇게 물어본다", "실무에서 이렇게 쓰인다" 추가 |
| **구체적 → 추상** | 예시·상황 먼저, 정의 나중. "이런 경우가 있다" → "그래서 이 개념이 필요하다" | 개념 설명 시 "상황 예시"를 앞에 두고, 정의는 뒤로 |
| **작은 단위** | 한 번에 하나. 인지 부하 관리. 15~20분이 한계 | 세션당 1개념, CS는 넓은 주제는 쪼개서 여러 개념으로 |
| **실패에서 학습** | 오답이 더 중요. "왜 틀렸는지" 구체적으로 | 오답 해설에 "이 선택지가 틀린 이유", "흔한 오해" 포함 |
| **자기 설명** | 남의 말로 읽기만 하면 까먹음. **내 말로 설명**하는 순간 이해도가 올라감 | 서술형 단계 유지·강화 |

## 3.2 설명 구조: "왜 → 뭐 → 어떻게"

주니어는 "이게 뭔데?"보다 **"이걸 왜 알아야 해?"**를 먼저 알아야 동기부여가 된다.

```
권장 순서:
1. 왜? - "이 개념을 모르면 면접/실무에서 이렇게 막힌다"
2. 뭐? - 정의, 핵심
3. 어떻게? - 동작 원리, 예시, 적용
```

→ **프롬프트 설계 시**: 개념 설명에 "이 개념이 왜 중요한가" 1~2문장을 맨 앞에 포함.

## 3.3 CS 개념 분할 원칙

CS는 한 개념당 설명량이 많다. **"교재 한 챕터"를 한 세션에 넣지 말고**, **한 세션에 담기 적당한 크기**로 쪼갠다.

| 나쁜 예 (너무 넓음) | 좋은 예 (세션 단위) |
|---------------------|---------------------|
| 해시 테이블 (전체) | 해시 테이블 기초, 해시 충돌 해결, 해시 시간복잡도 |
| 프로세스 스케줄링 (전체) | FCFS/SJF, 라운드 로빈, 우선순위 스케줄링 |
| TCP/IP (전체) | TCP vs UDP, 3-way handshake, TCP 연결 해제 |

**원칙**: 한 개념 = "15~20분 내에 설명 + 퀴즈 3개" 가능한 크기.

## 3.4 복습·간격 반복

- **약점 개념**은 한 번에 끝내지 말고, **일정 간격 후 재학습** 권장
- 대시보드 "약점 분석" → 해당 개념 재학습 세션 유도
- (장기) "N일 전 학습한 개념" 복습 알림

## 3.5 적응형 난이도

- 이전 점수 낮으면 → 다음 문제는 기본에 가깝게
- 이전 점수 높으면 → 더 어려운 응용/상황 문제
- (현재) `APPLICATION_QUESTION_PROMPT`에서 `previousScores` 반영 중

# 4. 도메인별 우선순위

공부 팁·추천 순서 및 취준/주니어 타깃을 반영한 우선순위:

| 순위 | 도메인 | 목적 | 대상 |
|------|--------|------|------|
| 1 | **자료구조 & 알고리즘** | 코딩테스트 대비 | 취준생 필수 |
| 2 | **운영체제 & 네트워크** | 기술면접 대비 | 취준생 필수 |
| 3 | **데이터베이스** | 실무 활용도 ↑ | 주니어 |
| 4 | **컴퓨터 구조** | 언어/OS 이해력 향상 | 심화 |
| 5 | **React** | 프론트엔드 실무 (JS 선수) | 주니어 |
| 6 | **시스템 설계** | 2~3년차 이후 확장 | 시니어 |
| 7 | **컴파일러/PL 이론** | 심화 (선택) | 심화 |

**v1 확장 권장 순서**: JavaScript(완료) → **자료구조&알고리즘** → **React** → **OS&네트워크** → **데이터베이스**

# 5. 개념 선정 기준

## 5.1 공통 원칙

1. **한 세션에 담기 적당한 크기** (15~30분 학습 가능)
2. **선수과목(prerequisite) 관계 명확** – 그래프 구조 유지
3. **LLM으로 설명·출제·평가 가능** – 코드 실행/컴파일 불필요
4. **면접/실무에서 자주 등장** – 검증된 주제 우선

# 8. CS vs JavaScript: 세션 플로우 차이

## 8.1 현재 JS 세션 플로우

```
1. 개념 설명 (EXPLAINING)
2. 객관식 1개 (OBJECTIVE)
3. 서술형 1개 (SUBJECTIVE)
4. 응용 문제 1개 (APPLICATION)  ← 코드 기반 실전 문제
5. 요약 & 숙련도 반영 (SUMMARY → CLOSED)
```

## 8.2 CS의 특수성

- **응용 문제(APPLICATION)의 한계**: JS는 "이 코드의 출력은?", "이 버그를 수정하라" 같은 **코드 기반** 응용이 가능. CS(자료구조, OS, 네트워크 등)는 코드 실행이 없어 **동일한 형태의 응용 문제 출제가 어렵다**.

## 8.3 제안: 도메인별 APPLICATION 프롬프트 분기

**세션 구조는 동일 유지**, APPLICATION 단계의 **프롬프트만 도메인별로 분기**.

| 도메인 | APPLICATION 문제 유형 | 예시 |
|--------|------------------------|------|
| **JavaScript** | 코드 기반 (실행 추론, 버그 수정) | "다음 코드의 출력은?" |
| **React** | 코드 기반 (컴포넌트 설계, 버그 수정) | "이 상황에서 어떤 Hook을 쓰는가?" |
| **CS 기초** | **상황/선택/추론 기반** | "다음 상황에서 어떤 자료구조를 선택하는가? 이유는?" / "이 알고리즘의 시간복잡도는?" |

### CS용 APPLICATION 프롬프트 예시 (개념)

```
"${conceptName}" 개념에 대한 상황 기반/추론 문제를 출제하세요.
- 코드 실행이 아닌, 개념 적용·선택·분석 능력을 평가
- 예: "실시간 채팅에서 메시지 순서 보장이 필요할 때 적합한 자료구조는?"
- 예: "이 스케줄링 알고리즘의 평균 대기시간을 설명하라"
```

### 구현 방향

1. **Concept 모델에 `domain` 필드 추가** (예: `javascript`, `react`, `dsa`, `os-network`, `database`)
2. **APPLICATION 단계**에서 `domain`에 따라 다른 프롬프트 호출
   - `javascript`, `react` → 기존 `APPLICATION_QUESTION_PROMPT` (코드 기반)
   - `dsa`, `os-network`, `database` 등 → `APPLICATION_QUESTION_PROMPT_CS` (상황/추론형)
3. **객관식·서술형**은 도메인 무관하게 동일 사용 (필요 시 `codeExample` 유무만 조정)

## 8.4 대안: CS 전용 세션 타입 (장기 검토)

CS만 **응용 단계 생략** 또는 **다른 단계로 대체**하는 방식:

- 예: 객관식 2개 + 서술형 2개 (응용 대신 서술형 비중 확대)
- 예: "상황 기반 객관식" 1개 추가

→ v1에서는 **8.3 (프롬프트 분기)** 로 충분. 사용자 반응 보고 8.4 검토.
